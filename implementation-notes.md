# Implementation notes

## Python requirements scan-version policy (2026-11-23)

- Select an exact `==`/`===` version first, otherwise the greatest `>=` bound, otherwise the least `<=` bound. Ignore `!=`, `>` and `<` when selecting values and checking conflicts.
- Conflicting exact values, contradictory inclusive bounds, an exact value outside inclusive bounds, and malformed/unsupported specifiers yield an empty version. Keep the package identity without inventing a version.
- Use `github.com/aquasecurity/go-pep440-version v0.0.1` for Python normalization and ordering. Equivalent spellings use a stable normalized representation independent of declaration order.
- The result is an ordinary scan version; original constraints and inference metadata are intentionally not retained. It is a boundary-check policy, not a reconstruction of installed versions.
- Each discovered requirements manifest produces its own dependency graph. Identical package/version identities from multiple manifests can be deduplicated downstream; different selected versions remain separate components.
- Keep one requirements parsing implementation inside this independently distributed tool. Mirror the policy contract tests with the sibling OpenSCA/MurphySec repository; no cross-tool runtime dependency is introduced.
- Run targeted tests with `rtk go test ./opensca/sca/python ./cmd/format ./cmd/detail .`. Build the current-platform CLI with `rtk go build .`; TanSpec's implementation notes document the shipped executable paths.

## Unified dependency endpoint audit (2026-11-24)

- Supersedes the earlier single-bound Python policy. All three production scan paths share the nested Go module `github.com/winezer0/opensca/versionaudit`, located in the sibling OpenSCA checkout's `versionaudit/` directory. TanSpec embeds the local OpenSCA checkout, and both TanSpec and MurphySec use an explicit local module replacement. Parser adapters preserve manifest declarations; the shared module alone selects audit versions.
- Actual lockfile/build evidence bypasses catalog selection. Explicit pins retain `declared_exact` provenance. Other supported constraints select the minimum and maximum matching published releases, deduplicating identical endpoints. An unavailable catalog uses only numeric/version boundaries literally present in the declaration, including excluded boundaries, marked `boundary_fallback`. Successful empty/no-match responses remain unresolved. Cancellation never triggers fallback.
- Python uses Aqua PEP 440 semantics, Composer uses `github.com/shyim/go-version`, and npm/Cargo/NuGet/Maven/RubyGems use their native implementations in `deps.dev/util/semver`. Composer's deps.dev implementation supports version parsing but panics on constraints, so it is not used for Composer comparison/matching. Gradle dynamic prefixes and Ivy alternate interval delimiters are recognized within the Maven ecosystem. Unsupported/malformed declarations, missing versions and source-only references remain versionless identities; no arbitrary adjacent release or implicit fallback ceiling is manufactured.
- OpenSCA normalizes declarations after parser graph construction and before CLI detail/PURL creation. MurphySec normalizes every inspector's modules before component collection. Candidate range nodes retain parent/directness/development/path evidence but do not reuse any guessed transitive dependency graph. Actual versions and exact pins retain their verified child graph.
- OpenSCA static npm, Composer, Python requirements/Pipfile/setup, Maven/Gradle and NuGet entry points retain constraints. MurphySec static npm, Composer, requirements/Poetry, Maven/Gradle, NuGet, Ivy and Gemfile entry points retain constraints; Gemfile preserves every quoted range term. Other inspectors pass through the same final normalization hook; actual lockfile versions remain actual. Unsupported native constraint schemes (including CPAN and LuaRocks) remain visibly unresolved rather than being interpreted as SemVer.
- Catalog access is independent of package installation/build commands. Shared administrator environment: `SCA_VERSION_DIRECTORY_OFFLINE=true|false`, `SCA_VERSION_DIRECTORY_CACHE=<directory>`, `SCA_VERSION_REGISTRIES={"npm":"https://registry.example","maven":"https://repo.example/maven2"}`. Aliases resolving to the same ecosystem cannot be configured twice. Registry credentials in URLs are rejected; existing application credentials are neither read nor modified by this work. Only configured metadata endpoints are queried; no project code is executed by catalog selection.
- TanSpec defaults all three paths to offline metadata access. Set `SCA_VERSION_DIRECTORY_OFFLINE=false` in the service environment to enable catalog HTTP for all paths while retaining existing no-build/offline dependency parsing. Existing external-engine environment overrides can also configure CLI access. Standalone OpenSCA can configure `version_audit` with `offline`, `cache_dir` and `registries` in its native JSON; its global offline setting remains effective unless explicitly overridden by the catalog environment.
- Supported HTTP catalogs: npm packument, PyPI JSON, NuGet PackageBaseAddress or same-host service-index discovery, RubyGems versions API, Packagist p2, crates.io and Maven metadata. Persistent successful metadata is keyed by registry and package, read before HTTP, expires after 24 hours online and remains usable offline. Request timeout is 10 seconds; individual responses/cache records are capped at 16 MiB. A per-scan session shares repeated requests and failures. Cache write failures are best effort and do not discard successfully fetched versions.
- Range declarations and `actual|declared_exact|published_endpoint|boundary_fallback|unresolved` provenance survive OpenSCA CycloneDX properties, MurphySec SPDX package comments, TanSpec SBOM round trips, analyzer snapshots, stored components and JSON report exports. Versionless components are retained for inventory statistics and excluded from matching for every ecosystem. An inventory containing only unmatched identities is stored with its coverage counts and fails with the existing no-scannable error instead of reporting a clean audit.
- All three analyzer cache policies were bumped. Cache identity includes catalog routing/environment, the UTC freshness day and, for CLI adapters, native configuration contents and process environment overrides. Existing task records are not rewritten, and no service is restarted.
- This remains endpoint sampling: intermediate versions can have additional vulnerabilities, and declaration fallback endpoints can lie outside an open interval or be unpublished. Provenance is essential for interpreting these audit candidates. No candidate-dependent transitive graph is claimed.
- Local executable build targets: `third/opensca/opensca-cli.exe` and `third/murphysec/murphysec-windows-amd64.exe` under TanSpec. No remote module release or repository push is performed.

- TanSpec component persistence adds `declared_version` and `version_source` columns. Per the development database policy, no migration is supplied: startup requires a fresh database or a schema already matching this build. Existing databases and history are not modified.

Validation: affected endpoint/parser/config/detail/format packages passed (170 tests); shared module passed `go test -race -cover ./...` with 82.1% statement coverage. Rebuilt the local CLI and passed TanSpec actual-binary parity tests.
